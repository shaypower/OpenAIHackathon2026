## Common wire rules

- Snake_case JSON over HTTP; frontend camelCase stays behind adapters. IDs are opaque nonempty strings, stable within a dataset version. No MapLibre/runtime/agent classes cross the wire.
- API success envelopes: `{"schema_version":1,"data":...}`. Every civic result/snapshot carries explicit `data_mode`: `synthetic`, `real`, or `mixed`. `real` identifies source-backed inputs, **not verified civic findings**; evidence verification, assumptions and engine support are separate.
- GeoJSON is the exception: return an RFC-style `FeatureCollection`, with additive top-level `schema_version`, `run_id`, `data_mode`, `comparison`, `generated_at`. Do not wrap it in `data` or invent a CRS member.
- WGS84 `[longitude, latitude]` (EPSG:4326); point/line/polygon/multipolygon only in initial schemas. Stable feature IDs, closed rings, valid polygon topology and no non-finite coordinates. Domain schemas bound coordinates/shape lengths; A/B validate topology/closure and geospatial meaning at their boundaries.
- Time durations are minutes; distances km; operational cost is **indicative EUR/week** with method/evidence. Timestamps include date and timezone offset; source update dates may retain date-only precision. Store UTC when possible; journeys retain named timezone and original GTFS service date. Frontend formats Europe/Dublin.
- Unknown values are null with an explanation, not zero. Zero cohort means `access_percent=null` and a no-demand limitation. Never invent a finite duration for no path. Never sum household and person counts or marginal cohorts as if they were disjoint.
- Required provenance labels are never inferred from a basemap. A run with any synthetic analytical input is synthetic/mixed as appropriate; evidence involving synthetic inputs cannot be `verified` public evidence. Preserve that through export and model explanation.
- Validate input and output structurally; models reject extra fields, invalid counts/percentages and NaN/infinity. Cross-record references, feasibility, support, counts and provenance truth require owner-side checks; a DTO validation pass is not factual proof.

## Shared domain vocabulary

Read exact field types/defaults from `backend/domain/models.py`. Import examples:

```python
from backend.domain.models import CivicObjective, Community, SimulationRun

objective = CivicObjective.model_validate(payload)
wire = objective.model_dump(mode="json")
schema = CivicObjective.model_json_schema()
```

| Model | Boundary and meaning |
| --- | --- |
| `Provenance` | Source/dataset/URL, known update date, actual acquisition timestamp, licence, real/synthetic, optional original record ID |
| `Evidence` | Claim + resolving provenance IDs + synthetic/unverified/verified state; no invented confidence score |
| `PopulationProfile` | Resident total, 65+ residents, no-car **households**, target-cohort residents and observed/estimated/unknown/synthetic cohort method |
| `CivicObjective` | Text, domain, service, geography/region, age/car constraints, maximum journey and optional coverage target |
| `DemandConfig` | Versioned explicit relevance/need/dependency/vulnerability weights and missing-data policy; no weighting algorithm |
| `Community`, `ServiceLocation` | Stable entities, WGS84 geography, population/service kind, provenance and data mode; service hours known flag |
| `Journey`, `JourneyLeg` | Dated, timezone-aware walk/transit/wait/transfer/service legs; feasibility and actual total or null |
| `FailureReason`, `AccessibilityResult` | Typed failure and cohort-specific deterministic access/counts; evidence/journey references |
| `Intervention`, `InterventionChange` | Proposal and explicit change parameters; **no invented pre-simulation impact** |
| `SimulationMetrics`, `SimulationRun` | Calculated results and before/after, immutable input IDs/config/engine, departure/timezone, lifecycle and evidence |
| `StressScenario` | Explicit edge/service/trip removals and display geometry; no preset percentage loss |
| `MapFeature` | Stable GeoJSON feature with entity/layer/state/data_mode/evidence metadata |

Only TimetableChange, FeederService and MobileService **schemas** exist now; none has backend execution. Unknown change kinds must be rejected. AdditionalDeparture, RouteExtension, NewStop and FacilityPlacement need a coordinated schema addition before execution. Keep service and journey mode extensible instead of hardcoding buses.

Semantic checks B/C must enforce: `reachable_residents <= cohort_residents`; percentage equals reachable/cohort × 100 (document rounding tolerance); chronological legs/duration totals and transfer constraints agree; duplicate IDs are rejected; referenced dataset/service/journey/evidence IDs resolve; stress IDs exist in the selected graph; terminal succeeded runs contain calculated results; failed/cancelled runs never publish a successful after-state. C retains assumptions/limitations alongside a run response. Model schemas intentionally contain no routing, ranking or provenance-verification algorithm.

## A → B/C snapshot contract

Proposed processed directory: `backend/data/processed/<dataset_id>/`. It does not exist yet. Immutable versions prevent an active run's baseline changing under it.

```json
{
  "schema_version": 1,
  "dataset_id": "synthetic-small-areas-v1",
  "region_id": "tipperary",
  "geography_vintage": "synthetic-fixture-v1",
  "data_mode": "synthetic",
  "ingested_at": "2026-10-04T12:00:00Z",
  "coordinate_system": "EPSG:4326",
  "files": {
    "communities": {"path":"communities.json","sha256":"<actual checksum>"},
    "services": {"path":"services.json","sha256":"<actual checksum>"},
    "provenance": {"path":"provenance.json","sha256":"<actual checksum>"}
  },
  "record_counts": {"communities": 1,"services": 1,"provenance": 1},
  "missing_fields": ["service_opening_hours"]
}
```

This is an example, not a generated artifact. File paths are relative to the snapshot directory, cannot escape it and must match checksums. Records in each file are arrays validating against the matching DTO. Services may be omitted until available; baseline must then report missing_data, not invent care locations. Acquisition metadata/checksums belong in the manifest, not routing code.

GTFS acquisition is a separate dated raw feed reference in the manifest/inventory with checksum, source URL/licence, valid service date range and retained agency timezone. A preserves tables/IDs; B validates service availability and builds the graph. Do not normalise GTFS into precomputed “travelMinutes” constants.

For a real `Provenance`, A must verify a genuine dataset source URL, actual acquisition timestamp, known licence or explicit licence gap, and stable record linkage. Source update date is null if unknown; preserve date-only precision instead of fabricating a time. `ingested_at` is the acquisition time, not the fixture's arbitrary authored timestamp. Inventory planned entries can have null timestamps/URL; those are not normalised records and do not validate as ingested provenance.

Inventory file format is currently implemented as `schema_version`, `inspected_on`, `real_civic_datasets_ingested`, and `sources[]`. Each entry has `id`, `name`, `dataset`, `category`, `priority`, `status`, `data_mode`, `source_url`, `source_updated_at`, `ingested_at`, `licence`, `local_paths`, and `notes`. Statuses: `PLANNED`, `BUNDLED`, `REMOTE_CONTEXT`; A may add `INGESTED`/`FAILED` only with evidence/error metadata. BUNDLED fixture/context is not civic ingestion. C's `/api/sources` must preserve these facts.

## B → C deterministic tool contract

**All functions below are PLANNED**, with a proposed public facade `backend/simulation/service.py`. Internal graph/demand types stay in B's zone. B/C should agree one concrete snapshot loader type in their handoff before implementing, rather than leaking graph internals into HTTP models.

```text
load_snapshot(dataset_id) -> validated B-owned snapshot
run_baseline(snapshot, objective: CivicObjective, departure_at, demand: DemandConfig)
  -> SimulationMetrics + AccessibilityResult[] + Journey[] + Evidence[] + MapFeature[]
find_failures(accessibility) -> failed AccessibilityResult[]
inspect_failure(snapshot, objective, result, journeys) -> FailureReason[] + Evidence[]
generate_candidates(snapshot, objective, failures, allowed_kinds, max_candidates)
  -> Intervention[]
simulate_candidate(snapshot, objective, departure_at, demand, baseline, intervention)
  -> same result bundle as run_baseline
stress_test_candidate(snapshot, objective, departure_at, demand, baseline, intervention, scenario)
  -> same result bundle as run_baseline
rank_candidates(evaluated_candidates, ranking_config_id)
  -> ordered {intervention_id, simulation_run_id, rank, score_components}[]
```

C assigns run/operation IDs and persists result bundles as `SimulationRun`; B does not own HTTP job state. Model tools are thin wrappers over these functions. `get_population` / `get_services` read A's validated records; they do not ask a model to estimate counts. Unsupported changes, invalid references, missing cohort/feed/graph and computation timeout return typed tool errors, propagated by C. C must not turn errors into quantitative defaults.

Initial cap: 20 candidate evaluations and one stress scenario per selection, within C's overall run deadline. All comparisons use identical objective, departure, dataset IDs and demand config. Ranking follows PERSON_B's explicit ordering; no hidden policy constants in routing or an LLM-assigned score.

The first candidate search preserves access for already reachable target-cohort residents. Re-evaluate impacted transfers across the scoped network before ranking; shifting one connection can break another. If future policy permits losses, report those and net gain explicitly through a coordinated metric contract rather than selecting a high-gain proposal that silently removes existing access.

## Planned HTTP payloads

Examples below are **illustrative contract samples, not API readbacks**. Implement request models in `backend/api/`. Reject unknown fields. IDs resolve server-side; clients send IDs, not their own metric/geometry patches. Initial region is Tipperary only if the capability response explicitly says so.

### GET /api/status — PLANNED

200 data: `status` (`ready` / `degraded`), `data_mode`, `capabilities`, `supported_regions`, `supported_intervention_kinds`, `limits`, `run_store`. Example capability record: `{"name":"baseline","status":"PLANNED"}`. Limits name maximum candidates/tool steps/deadline; run_store states memory/durable, TTL/restart behaviour. Until implemented, use `/api/` solely for health.

### GET /api/sources — PLANNED

200 data: the inventory object described above. Do not claim planned sources ingested. Do not expose secrets, private cache paths or fetch credentials. Source URLs are dataset citations, not authenticated download links.

### GET /api/communities — PLANNED

Query: required `region_id`; optional `dataset_id` (otherwise current validated snapshot), `limit` (default 100, maximum 500), `cursor` (opaque). Stable ID ordering within the pinned snapshot. 200 data: `{"dataset_id":"...","data_mode":"...","items":[Community],"provenance":[Provenance],"next_cursor":null}`. Include all provenance referenced on that page. `next_cursor` binds dataset/filter/order; dataset replacement must not silently change the next page. Unknown region/snapshot gives 404; unavailable data gives 503.

### GET /api/communities/{id} — PLANNED

Query: required `dataset_id`; optional `run_id` for evaluated context. 200 data: `community: Community`, `provenance: Provenance[]`, `analysis: AccessibilityResult|null`, `journeys: Journey[]`, `evidence: Evidence[]`. Without a run return analysis null and no computed journeys, not global latest values. A requested run must contain that community and match the snapshot; otherwise 409. This supports selection/inspection. Root-cause descriptions and evidence are from tool results, not fake citations.

### POST /api/objectives/analyse — PLANNED

```json
{
  "text": "Make primary healthcare reachable within 45 minutes for elderly people without cars in rural Tipperary.",
  "departure_at": "2026-10-05T07:00:00+01:00",
  "timezone": "Europe/Dublin",
  "dataset_ids": ["synthetic-small-areas-v1","synthetic-transit-v1"],
  "demand_config_id": "synthetic-demand-v1",
  "client_request_id": "<unique request id>"
}
```

Text 12–500 characters after trim, aware dated departure, named IANA timezone, known nonempty dataset IDs/config. Compilation/semantic validation happen before accepting a baseline run; explicit defaults are returned as assumptions. 202 data:

```json
{
  "run_id": "run-example",
  "status": "queued",
  "data_mode": "synthetic",
  "objective": {
    "id":"objective-example",
    "text":"Make primary healthcare reachable within 45 minutes for elderly people without cars in rural Tipperary.",
    "domain":"healthcare",
    "target_service":"primary_care",
    "geography":"rural Tipperary",
    "region_id":"tipperary",
    "population":{"min_age":65,"car_access":false},
    "constraint":{"maximum_journey_minutes":45,"target_access_percent":null},
    "objective":"maximize_accessibility"
  },
  "assumptions": [],
  "poll_url": "/api/runs/run-example"
}
```

The structured objective contains **no calculated population or impact fields**. An absent journey bound/ambiguous geography is an assumption/clarification, not an invisible fabricated requirement. Unsupported intent gives 422 `unsupported_objective`. Successful acceptance is not completion. No model endpoint is implemented by this documentation.

### GET /api/runs/{run_id} — PLANNED

200 data: `{"run":SimulationRun,"assumptions":[],"limitations":[],"ranking":[]}`. Ranking entries, if any, are `{intervention_id,simulation_run_id,rank,score_components}` from B. Evidence/provenance arrays in run resolve referenced IDs. `before`/`after` are null while uncomputed; a candidate preview cannot set succeeded. Engine/config/dataset versions bind all metrics. Lifecycle `queued → running → succeeded|failed|cancelled` is terminal; never silently resubmit a failed run.

Poll initially every 1000 ms while active, stop at terminal status or a 30-second client deadline. Network failure keeps last snapshot with a recoverable message; do not switch to fixtures. 404 unknown run; 410 expired (if tombstones retained). In-memory MVP can instead return 404 after restart/eviction with restart loss disclosed. No server-cancellation route exists in v1; browser abort stops observation only. Persistent execution/reconnect/SSE is a later coordinated change.

### GET /api/runs/{run_id}/geojson — PLANNED

Query `comparison=before|after` (default before). 200 FeatureCollection with top-level metadata and `MapFeature[]`. Feature properties have `entity_id`, `label`, `layer`, `state`, `data_mode`, `evidence_ids`; IDs must stay stable across before/after for selection. Before returns pinned baseline features; after returns computed candidate/stress coverage/network only when that result exists. Uncomputed after gives 409 `result_not_ready`, never guessed coverage. Point/line features alone do not prove reachability; coverage derives from B's results.

### POST /api/interventions/generate — PLANNED

Request: `baseline_run_id`, nonempty `community_ids`, `allowed_kinds` (supported typed changes), `max_candidates` (integer 1–20), `client_request_id`, optional `scenario_id` + `intervention_id` **together** for contingency. IDs must refer to the same objective/snapshot. If the pair is absent, generate ordinary baseline candidates. Unsupported kind gives 422; incomplete/contradictory IDs give 422/409. 200 data: `{"baseline_run_id":"...","data_mode":"...","items":[Intervention],"evaluations":[]}`. Evaluations may reference **completed deterministic** simulation runs with rank; without them the proposal is unscored. Do not populate impact from LLM text or browser fixtures.

### POST /api/simulations/run — PLANNED

Request: `{"baseline_run_id":"...","intervention_id":"...","client_request_id":"..."}`. Baseline must be succeeded and candidate must belong to it; mismatched run/snapshot gives 409. 202 data: `run_id`, `status`, `data_mode`, `poll_url`. C stores kind `intervention` with baseline/candidate IDs. B computes unchanged baseline and after under the same config; the run response supplies calculated metrics.

### POST /api/stress-tests/run — PLANNED

Request: `{"simulation_run_id":"...","scenario_id":"...","client_request_id":"..."}`. Requires succeeded candidate simulation and compatible scenario; reject unknown graph/trip/service IDs. 202 data uses the same acceptance fields. The new run kind is `stress_test`, linked to the original baseline, candidate and scenario. Its before/after compare selected intervention before disruption vs recomputed disrupted outcome; `baseline_run_id` still identifies original baseline. No fixed percentage subtraction is permitted in the deterministic engine. Existing local mock subtraction remains labelled mock.

### Additional D provider responses — PLANNED

`/api/services`: same pinned-pagination rules as communities; data includes `dataset_id`, `data_mode`, `items: ServiceLocation[]`, resolving `provenance`, `next_cursor`.

`/api/transport`: query required `region_id`/optional pinned `dataset_id`; data includes `dataset_id`, `data_mode`, `routes`, `stops`, `provenance`. Initial map-only routes: `{id,name,geometry:LineString,stop_ids,status:existing|proposed|disrupted,provenance_ids}`; stops: `{id,name,geometry:Point,provenance_ids}`. These DTOs belong to C's API layer when implemented; they do not replace B's timetable graph. Large feeds need an agreed bounding/pagination strategy before exposure.

`/api/stress-scenarios`: data includes `data_mode`, `items: StressScenario[]`, resolving `provenance`. D's current provider accessor is synchronous; initialise its cache during bootstrap or coordinate an async interface change. Do not block React render on HTTP or smuggle a fetch into getStressScenarios.

## Errors, replay and execution bounds — PLANNED

```json
{
  "schema_version":1,
  "error":{
    "code":"unsupported_intervention",
    "message":"This engine does not evaluate that change kind.",
    "request_id":"request-example",
    "retryable":false,
    "details":{"supported_kinds":["timetable_change"]}
  }
}
```

HTTP: 422 invalid/unsupported objective, change or field; 404 unknown ID; 409 stale/incompatible snapshot, unfinished result or conflicting idempotency key; 429 bounded capacity; 503 missing data/dependency/provider; 504 execution deadline. Do not log keys, send stack traces or expose private model runtime. FastAPI's current default 422 shape has not been replaced; C implements this envelope before D depends on it.

All mutation requests require `client_request_id` (nonempty ≤160 chars). C binds it to method + normalised payload + local session/actor where applicable. Exact replay returns the original result/run; different payload is 409. Recheck uncertain request status before replay; no duplicate paid action. Public multiuser deployment/auth is outside this slice and needs explicit design; do not invent an owner identity from client fields.

Proposed bounds: C one active run/session, 12 tool actions, 30 seconds/run, one refinement, configured model token/cost budget and one transient retry within deadline. B 20 candidate evaluations. Memory store 100 runs/one-hour TTL/single worker, with restart loss disclosed. These are targets, not existing enforcement. D's current mock hook has a 12-second operation/8-second inspection timeout; D must adapt deadlines for actual accepted jobs rather than silently timing out a 30-second backend run.
